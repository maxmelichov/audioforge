# audioforge on the two-RTX-5090 box (2026-09-29)

2026-09-29. Request: "test audioforge on the 5090 and upload a PR with the results", refined during the run to
"test whether it works on the 5090, and push any optimisation you find", "do all the testing we had on Pipecat and
LiveKit as well", and "the training runs only if the rest is done and the student checkpoint is available". This
note is the record of that run. The numbers are in `runs/gpu_run_2026-09-29.json`, built by
`scripts/research/gpu_run_5090/build_results.py`. The tools that produced them are in
`scripts/research/gpu_run_5090/`.

## Verdict

- **It works on the 5090 box after four small fixes.** Every fix is a bug on a fresh Linux clone, not a
  Blackwell problem:
  - `api.load` / `audioforge-bench` did not find the downloaded Silero, and they crash without `lid_distill.pt`;
  - `gate.sh` is macOS-only and hangs on Linux;
  - a final-ASR worker that dies while loading hangs the server;
  - two research drivers write to the laptop's scratch paths.

  PyTorch 2.11 + cu128 runs on sm_120 with bf16. The fast CI subset passes on CPU except one test that is
  seed-dependent on this platform. That test also fails with torch 2.14 and on unmodified `main`.
- **Optimisation: `--device cuda` for the streaming server (opt-in).** It runs the same code with the models on the
  GPU and gives the same events as the CPU. Compute per 160 ms block drops from 77 to 20 ms (p50) in single mode, and
  room mode goes from RTF 1.02 to 0.16. One server process holds **4 live sessions** in real time on a GPU, against
  **1** on 2 CPU threads.
- **A correctness bug found only in a real LiveKit room.** PyTorch's default cuDNN TF32 moves the encoder output
  1.5 % from CPU, and that flipped the transcript of the bundled call in 2 of 3 live runs. `--device cuda` now runs
  full fp32. The difference is then 5.6e-6, and the speed cost could not be measured.
- **This CPU is slower than the laptop for this workload.** The published protocol is 2 threads per model. At 2
  threads the Ryzen 9 7950X runs single mode at RTF 0.54–0.62 (M5: 0.33) and room mode at RTF 1.02–1.07 (M5:
  0.64). **Room mode does not keep real time on 2 x86 threads**: all 48 live CN sessions were flagged as overloaded
  (RTF > 1). The GPU restores it.
- **Live through Pipecat, single mode reproduces the published row on this box.** 3 s misses are 37.67 %, the same
  as published; cut-ins are 0.68 vs 0.67 per session; WER is 0.2321, the same as published; dead air is +54 ms. With
  `--device cuda` the row is equivalent: 37.2 %, 0.65, 0.2321, 1408 ms.
- **The single-model distillation (S1/S2/S3) was not run.** The student is not the blocker: `audioforge-download
  --heads-version 0.1` rebuilds `runs/stage1_served.afm` bit-identical. The AMI / ICSI host served about 4 KB/s per
  connection today, so the ~19 GB of training meetings would take days. Both GPUs were also mostly held by another
  user job for the whole session. No pre-registered bar was measured.

## 2. `--device cuda` (opt-in)

Before this run, `Engine.load` sent every device to the CPU ("the streaming path is CPU-only"). The only change
needed was to put host-made tensors on the model's device. That covers the turn head's inputs, the kernel pass's
activity, the LID keep mask, the TS-VAD head and the `ColumnEmbedder` inputs, plus `.cpu()` before `.numpy()`.
fast-conv (a CPU path) is off on the GPU. `audioforge-serve --device cuda`, `audioforge-bench --device cuda` and
`audioforge.load(device="cuda")` select it. Without a GPU, and for `mps`, the old fallback to CPU stays.

**Same events as the CPU** on the bundled clips:
- single mode with a stored print, with `fe.voiceprint`, and with arm-after-`agent_end`;
- room mode with Nemotron-3, with and without `--final-asr tdt_v3`;
- 6 client block sizes (10 ms – 160 ms and random);
- live through Pipecat on all 69 E2E sessions (§4): the same WER, and 16 / 16 identical transcripts on the TurnBench
  mono set.

**Speed, bundled 16 s two-party clip, 2 threads, best of 3 after warm-up.** The published column is the README's
M5 output.

| | M5 laptop CPU (published) | 5090 box CPU | 5090 box CUDA |
|---|---|---|---|
| single mode, server (quickstart), RTF / chunk p50 / p95 ms | 0.336 / 53.7 / 57.5 | 0.498 / 78.1 / 85.2 (CPU-shared) | 0.160 / 24.9 / 27.1 (GPU shared) |
| single mode, in process (probe), RTF / block p50 / p95 ms, **idle GPU 0, 19:55** | – | 0.486 / 77.4 / 83.9 | **0.130 / 19.9 / 22.2** |
| single mode, `audioforge-bench`, GPU 1 shared, 22:20 | – | 0.537 / 84.8 / 94.4 | 0.162 / 25.3 / 28.1 |
| room mode (Nemotron-3), `audioforge-bench`, **idle GPU 0, 19:58** | 0.64 (live, E2E) | 1.022 / 180.9 / 304.7 | **0.162 / 27.8 / 39.4** |
| room mode, `audioforge-bench`, GPU 1 shared, 22:20 | – | 1.070 / 193.7 / 308.0 | 0.191 / 33.3 / 47.0 |
| Python API example (README), RTF | 0.196 | 0.49 | 0.14 |
| peak memory | RSS 1.14 GB | RSS 1.44 GB | RSS 1.67 GB; 517 MB CUDA allocated (torch peak), ~1.2 GB per server process in nvidia-smi |

The first CUDA numbers were taken with TF32 on. Full fp32 measured the same (probe on the shared GPU 1:
TF32 on 0.152–0.160 RTF, TF32 off 0.135–0.154), because per-frame decoding in Python dominates.

**Concurrent live sessions** (`concurrency.py`, one server process, N clients at 1x with staggered starts, single
mode). Latency is the frame's arrival time minus its `t` (the frame's audio end):

| N sessions | CUDA: p95 latency max / growth over the clip | CPU 2 threads: same |
|---|---|---|
| 1 | 107 ms / none | 186 ms / none |
| 2 | 120 ms / none | **2151 ms / +1.6 s (falls behind)** |
| 4 | **159 ms / none** | – |
| 8 | 2189 ms / +1.7 s (falls behind) | – |

Every session's finals equal the solo run's at every N. The server's one executor thread runs the sessions one
after another, so a GPU server holds about 4 real-time sessions (4 x ~30 ms per 160 ms), where 2 CPU threads hold
1. This recovers the number research/PERFORMANCE.md §2 left to "GPU production". The GPU was shared with another
job during this measurement.

**Final ASR on CUDA** (`--final-asr tdt_v3 --final-asr-device cuda`, room mode, CPU streaming engine):
- The same TDT text as the CPU pass.
- Per-turn latency p50 483 → 145 ms (10 s clip, 2 turns) and 1091 → 283 ms (16 s clip, 1 turn).
- With the streaming engine also on the same shared GPU (4 GB free), the TDT child died while loading and the
  server hung: finding 4. It now fails fast.

## 3. TF32: a CUDA-only transcription error

The in-process parity checks passed with PyTorch's defaults. A real LiveKit room did not.

Setup: `docker run livekit/livekit-server --dev` (v1.13.7), `examples/livekit_agent_worker.py dev`,
`examples/livekit_publish_wav.py` with the bundled call, and the audio going through WebRTC / Opus.

| server | caller's final transcript (3 runs each) |
|---|---|
| CPU | "so um what value guides your life what values you live by" x 3 |
| CUDA, PyTorch defaults (cuDNN TF32 on) | "so an overvalued guide your life overvalues you need by" x 2, the correct text x 1 |
| CUDA, TF32 off (this branch) | the correct text x 3 |

`tf32_probe.py` measures the encoder output on the bundled clip against CPU:
- with cuDNN TF32 on: relative L2 difference 1.5 %, max abs 0.19;
- with TF32 off: 5.6e-6 and 3.9e-5.

Live through Pipecat (§4), the TurnBench mono transcripts with TF32 on matched CPU on 13 of 16 sessions. With TF32
off they matched on 16 of 16 (and on 7 of 7 user-channel sessions). `Engine.load(device="cuda")` now sets
`torch.backends.cudnn.allow_tf32 = False` and `torch.backends.cuda.matmul.allow_tf32 = False` for the process.
Any other CUDA path in the repo that should match CPU numerics needs the same setting. The offline final-ASR child
process (`--final-asr-device cuda`) does not set it yet.
